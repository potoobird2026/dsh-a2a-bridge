# 明确不做的能力（Non-goals）

本文件记录**经项目所有者逐项确认后决定不做**的能力，以及每条的理由。目的是避免同一个议题在后续开发中反复被重新提出、反复讨论。

判定原则：一项能力只有在它**解决真实痛点**、且**成本与风险相称**时才进入路线图。以下四项都不满足。

---

## 1. Push notifications（被动推送）

**能力**：远端主动把任务状态推给调用方，而不是调用方轮询 `GetTask`。

**不做的理由**：

- 当前轮询已经能拿到结果，`GetTask` 的状态机在真机上验证通过（含 `CancelTask` 的 `-32002` 语义）。
- 推送省的是带宽，不是省事：它引入一个新的长连接、一套订阅生命周期、以及"推送丢了怎么办"的补偿逻辑。
- 协议里 `capabilities.pushNotifications` 保持 `false` 是**诚实的**——声明了却不用是最差的状态。

**若将来要做**：先确认调用方真的会因为轮询而错过时限，否则不划算。

---

## 2. mTLS（双向证书认证）

**能力**：双方各自用客户端证书互相认证，替代当前 Bearer token。

**不做的理由**：

- 当前部署形态是**局域网内两台自己的机器**，token 由两端的凭据存储管理，威胁模型里没有被 token 覆盖的中间人场景。
- mTLS 带来的成本是证书签发、轮换、过期处理、以及两端重启时的握手故障排查——这些运维负担远大于收益。
- 安全文档里已经写明：跨公网部署需要额外的传输层保护，届时优先考虑放在 TLS 反向代理之后，而不是把证书逻辑塞进插件。

---

## 3. 出站地址白名单（SSRF 面）

**能力**：限制出站请求只能连到允许的地址段，阻断指向元数据地址/内网服务的请求。

**不做的理由**：

- 出站 URL **只来自运维在 `outbound.contacts` 里写的配置**。peer 与模型都无法提供 URL，因此当前不存在"由对方驱动"的 SSRF 通路。
- 一旦将来允许模型或对端给出 URL，**必须先补上地址策略再开放该能力**——这条限制已经写进 `docs/threat-model.md` §4.2 的未实现项清单。

**注意**：`security-setup.md` 与 `troubleshooting.md` 曾经**错误地宣称**这个策略已经存在（还编造了一个不存在的 `skip` 开关）。已在 v1 修正为描述真实行为。这类"文档声称有、代码里没有"的偏差比功能缺失更危险。

---

## 4. 多身份（`/agents/<id>`）

**能力**：同一台 DSH 对外暴露多个不同配置的 agent 身份，远端可以点名调用其中之一。

**不做的理由**：

- 当前是**一台 PC 一个身份**，两台机器各一个，已经满足实际使用。
- 多身份是为"多团队共用一台主机"设计的，会同时引入身份路由、按身份隔离工作区与会话、按身份配置凭据等一串问题。
- 现在做等于为一个还没出现的场景预付复杂度。

---

## 附：被批准但尚未实现的一项

**A2A 会话的工具禁用名单**——项目所有者已确认要加限制，属于**待实现**（不是 non-goal）。

目标：A2A 会话里运行的 Agent 默认能调用宿主的全部工具，其中包括检索本机其它会话历史的工具。跨机器接入时不应顺带把本机历史对话暴露给局域网另一端。

实现前提（尚未确定）：需要先确认"按会话限制工具"的可用接缝——是通过 agent preset 组合限制，还是在工具注册层过滤。**在确认接缝之前不动手**，因为基于猜测的实现会把限制做成"看起来有、实际不生效"的样子，比没有更糟。
